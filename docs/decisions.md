# 決定事項と未決事項

コンセプト（[concept.md](concept.md)）から設計に落とす時に決めたこと、まだ決めていないことの一覧。設計ドキュメントはすべてこの表に従う。食い違ったらこの表を直してから他を直す。

## 前提

- ハッカソンの題材。デモで体験が伝わることを優先する。
- 法務・決済・物流の本番対応は後で詰める。ただし、後から本番化できなくなる作りは避ける。

## 決定

| # | 内容 | 理由 |
| --- | --- | --- |
| D1 | 贈る人は、ギフトを確定する前に会員登録とサインインをする。匿名ログインは使わない。候補を見るところまではログイン不要。 | 贈る人には状況と「開けたよ」を見せる宛先が要る。匿名アカウントの引き継ぎという複雑さを持ち込まない。 |
| D2 | 受け取る人はアカウントなしで受け取れる。リンクを開いて住所を入れるだけ。 | 友人の輪に広げるため。受け取りの手間を増やさない。 |
| D3 | 記録は本人だけのもの。日本酒と出会った記録で、自分で見返す、自分で選ぶ時の基準に使う。ギフトの候補選びには使わない。 | 贈りものは贈る人の気持ちが大事で、相手にとって新しいか、昔飲んだことがあるかは問わない。何度も飲みたいなら自分で買えばよい。 |
| D4 | 「開けたよ」は任意。受け取った一本を記録する時に、送るかどうかを本人が選ぶ。 | 手応えではあるが、受け取る人に義務を感じさせない。 |
| D5 | GET リクエストで状態を変えない。 | LINE のリンクプレビューやセキュリティスキャナが、人より先にリンクを開く。 |
| D6 | 期限は `*_expires_at` 列とリクエスト時の比較で判定する。期限切れを定期実行で書き換えない。 | 仕組みが単純。今は定期実行を使わない。 |
| D7 | （仮）公開の入口を 1 つにする。アプリもブラウザも Web の Worker にだけ話し、`/api/*` は Web がサービスバインディングで API に渡す。API の Worker は公開しない。 | オリジンが 1 つになり、CORS も Cookie の扱いも単純になる。独自ドメインがなくても workers.dev のまま成り立つ。独自ドメインは後から Web の Worker に付けるだけ。 |
| D8 | 住所フォームは一般的な形にする。郵便番号、都道府県、市区町村、番地、建物名、氏名、電話番号。 | 画面設計の前に決め打ちしてよい部分。 |
| D9 | Web とアプリは最終的にどちらもフル機能。最初はアプリと、Web の受け取りリンクだけを作る。 | ギフトを探す段階でアプリを入れさせないのが Web の役割。まずアプリで体験を作る。 |
| D10 | ギフトのキャンセルは、受け取られる前に贈った本人だけができる。受け取られた後は贈る人からキャンセルできない。画面と文書の言葉は「取り消し」ではなく「キャンセル」。 | 選び間違いや気が変わった時のため。受け取った相手は届くのを待っているので、後からは止めない。 |
| D11 | リンクの作り直しは、受け取られる前ならいつでもできる。新しいリンクに替わり、古いリンクは使えなくなる。 | 違う人に送った、グループに貼ってしまった時に、ギフトはそのままで古いリンクだけを止められる。 |
| D12 | キャンセルされたリンク、期限切れのリンク、作り直し前の古いリンクは、受け取る人に同じ文面を出す。「このリンクは使えなくなりました。贈ってくれた人に確認してください」程度。 | 「キャンセルされました」は相手に気まずい。どちらなのかも相手には分からないようにする。 |
| D13 | 受け取る人が断るボタンは置かない。受け取らなければ期限切れになる。 | 断ったことが贈る人に伝わるのは気まずい。 |
| D14 | すべてデモとして作る。代金を受け取らず、実際に買うことも送ることもしない。受け取りで住所と手配のデータはできるが、手配の状態は運営画面から手で進める。 | ハッカソンでは体験の流れを見せることを優先する。決済、物流、法務を持ち込まない。 |
| D15 | 予算は商品の価格だけで比べる。送料は扱わない。 | D14 で送らないため。 |
| D16 | 20 歳以上の確認と「20 歳未満の者の飲酒は法律で禁止されています」の表示は、体験の一部として定型文で置く。住所の使い道への同意文は置かず、代わりにデモで実際には届かないことを書く。 | 酒を扱うアプリとしての体裁は見せる。実際に住所を使わないので同意は要らない。 |
| D17 | ストアには出さない。アプリは Expo Go、受け取りリンクは Web でだけ動かす。Development Build、ストアの審査、ソーシャルログイン、Universal Links など、ネイティブのビルドが前提のものは使わない。Expo Go で動かないライブラリも使わない。 | ハッカソンのデモでは Expo Go で十分。Apple Developer Program などの費用と手間をかけない。 |
| D18 | 贈る人への知らせは、アプリ内の状況表示で見せる。プッシュ通知を前提にしない。 | Android の Expo Go ではプッシュ通知が届かず、iPhone の Expo Go でも設定の手間がある。演出として足すかは後で決める。 |
| D19 | 画面の言葉はすべて丁寧語。アプリ、LINE の定型文、受け取りページで揃える。 | 落ち着いた贈りものの印象にする。 |
| D20 | 候補の本数は決めない。予算内の候補をすべて見せ、情報を読んで選んでもらう。先頭の 2 本に「おすすめ・定番」と「おすすめ・定番以外」の印を付け、「誕生日に贈るなら、まずはこの一本です」のような一文を添える。 | 選ぶのは贈る人の感性に委ねつつ、迷った時の足がかりを先頭に置く。 |
| D21 | 候補は 1 枚ずつ左右にめくって見せる。 | 1 本ずつ説明を読んでもらう。 |
| D22 | 見た目はギフト EC を基調に、差し色に藍を少し使う。書体は Zen Kaku Gothic New。 | 日本酒を知らない人が身構えない、軽くてやさしい印象。 |

### D14 の運用

- 贈る人には一本の価格を目安として見せる。確定の画面で「デモのため購入も発送も行われません」と書く。
- 受け取りページとフォームにも、デモで実際には届かないこと、実在の住所を入れる必要はないことを書く。
- 手配の状態（手配済み、発送、届いた）は運営画面から手で進める。これがデモの操作そのものになる。

本番に進む時に足すもの: 決済、手配の方法（運営が代わりに買う、提携酒販店、既存のソーシャルギフト）、送料、住所の扱いと削除、法定表示と同意の確認。運営が代金を預かって酒を買い届ける形は、免許の確認が必須。
