# 認証・認可

前提: [decisions.md](decisions.md) の D1〜D7、[flows.md](flows.md)。

## 誰がアカウントを持つか

| 役割 | アカウント | いつ作るか |
| --- | --- | --- |
| 贈る人 | 必要 | ギフトを確定する直前（G5）。候補を見るまでは不要 |
| 受け取る人 | 不要 | 受け取りはリンクだけ。記録や開けたよを使いたくなった時に作る |
| 運営 | 必要、role=admin | 最初のサインインで付与 |

匿名ログインは使わない（D1）。アカウントは 1 種類で、贈る人と受け取る人の区別は持たない。同じ人がどちらにもなる。

## 方式

- **Better Auth** を apps/api に置く。drizzle アダプタで D1 に `user`、`session`、`account`、`verification` を持つ。
- **サインイン手段はメール OTP**。6 桁のコードをメールで送る。パスワードは持たない。
- Apple や Google のサインインは使わない。Expo Go ではリダイレクトの扱いが難しく、ストアにも出さないため（D17）。
- **メール送信**は Resend などの外部サービスか Cloudflare のメール送信。staging では送らずログに出す。
- **成人の自己申告**は、贈る人は会員登録時に `user.adult_confirmed_at`、受け取る人は受け取りフォームで `fulfillments.adult_confirmed_at` に残す。

## セッションの運び方

公開の入口は Web の Worker だけ（D7）なので、アプリもブラウザも同じオリジンに話す。

- Better Auth の `baseURL` は公開の入口のオリジン。`basePath` は `/api/auth`。Web が `/api/*` を API に渡すので、API から見ても同じ URL になる。
- **アプリ**: `@better-auth/expo` が Cookie を SecureStore に保存し、型付きクライアントの fetch に Cookie ヘッダを付ける。Expo Go で動かすので、`trustedOrigins` には Expo Go の `exp://` を入れる（D17）。
- **将来の Web 版**: 同じオリジンの Cookie がそのまま使える。
- 開発時は `BETTER_AUTH_URL` を mode ごとに変える。

## 受け取りトークン

- 32 バイトの乱数を base64url にしたもの（43 文字）。推測できないことが唯一の防御なので、短縮や連番にしない。
- DB には SHA-256 のハッシュ `claim_token_hash` を保存し、検索はハッシュで行う。DB が漏れても使えるリンクは漏れない。
- 贈る人がリンクを後から再表示できるように、トークン自体は Worker の秘密鍵で暗号化した `claim_token_enc` にも持つ。AES-GCM、鍵は `CLAIM_TOKEN_KEY`。
- 有効期限は `token_expires_at` の 1 列で、状態が進むたびに延ばす。期限の表は [flows.md](flows.md) の「リンクの有効期限」。
- トークンでできること:
  - 受け取りページの閲覧。状態によって出すものが変わる
  - 住所の送信。1 回だけ
  - アプリへの紐づけ。受け取り後、有効期限内だけ
- トークンでできないこと: 送信済みの住所を読むこと。贈る人の連絡先を知ること。キャンセルか期限切れかを知ること（D12）。
- URL と LINE のプレビューに個人情報を出さない。OGP は「日本酒が届きます」程度に留め、贈る人の名前や一言は出さない。プレビューはグループでも見えるため。
- GET では何も書き込まない（D5）。閲覧の記録も取らない。

## 受け取る人のアカウントへの紐づけ

経路は [flows.md](flows.md) の 2 つ。どの経路でも同じ service を通し、次を守る。

- 紐づけられるのは `claimed` のギフトで、トークンの有効期限内のものだけ。
- 1 つのギフトに紐づくアカウントは 1 つ。すでに別のアカウントに紐づいていたら失敗にする。
- 贈った本人のアカウントには紐づけない。
- メールでの自動紐づけは、メール OTP で確認済みのアドレスが、受け取りフォームに入力されたアドレスと一致した時だけ。会員登録の時と、サインインのたびに確認する。
- 紐づけても贈る人には何も通知しない。

## 認可

| 操作 | 未ログイン | ログイン中の本人 | 受け取りトークン | admin |
| --- | --- | --- | --- | --- |
| カタログの閲覧、候補の計算 | ○ | ○ | ○ 選ばれた一本だけ | ○ |
| ギフトの確定 | × | ○ | × | ○ |
| 贈ったギフトの状況、リンクの再表示と作り直し | × | ○ 贈った本人だけ | × | ○ |
| ギフトのキャンセル | × | ○ 贈った本人だけ、受け取られる前 | × | ○ |
| 受け取りページの閲覧 | - | - | ○ 住所以外 | ○ |
| 住所の送信 | - | - | ○ 1 回 | ○ |
| 住所の閲覧 | × | × 贈った本人も不可 | × | ○ 運営画面で |
| もらったギフトの紐づけ | × | ○ | ○ トークンを持つ本人 | - |
| 開けたよの送信 | × | ○ 紐づいた本人、1 回 | × | × |
| 記録の作成、閲覧 | × | ○ 自分のものだけ | × | × 運営も読まない |
| 手配の一覧と更新 | × | × | × | ○ |

原則:
- 贈る人は、受け取る人の住所、メール、アカウントの有無、記録を一切見ない。見えるのは状況と、開けたよが届いた事実だけ。
- 記録はギフトの候補選びにも、運営の集計にも使わない（D3）。
- 所有者の確認は service の中で行う。ルートの書き忘れで漏れないようにする。

## 実装メモ

- `middleware/session.ts`: `auth.api.getSession({ headers })` の結果を `c.set("user", ...)`。未ログインは null のまま通す。
- `middleware/require.ts`: `requireUser`、`requireAdmin`。
- admin の付与: 秘密情報 `ADMIN_EMAILS` に含まれるメールで会員登録したら `role = "admin"` にする。Better Auth の databaseHooks で行う。
- レート制限: メール OTP の送信と検証は Better Auth 内蔵のもの。受け取りの POST は Web の Worker でレート制限バインディングを使う。
- CSRF: 受け取りフォームの POST は Hono の csrf ミドルウェアで Origin を確認する。
- 監査: 状態の変化はすべて `gift_events` に残す。誰が、いつ、何をしたか。
