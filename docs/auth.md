# 認証・認可の設計

## 登場人物と必要なもの

| 役割 | 入口 | アカウント | 根拠 |
| --- | --- | --- | --- |
| 贈る側 | アプリ（将来 Web も） | 必要。ただしリンク発行までは匿名で進められる | 「開けたよ」を受け取る宛先と、決済の主体が要る |
| 受け取る側 | 受け取りリンク（Web） | 不要 | リンクだけで完結させる。URL のトークンが権限そのもの |
| 記録を付ける人 | アプリ | 必要 | 本人だけが見られる私的データ。端末を変えても残す |
| 運営（自分） | アプリ / API | 必要 + role=admin | 注文の手動進行、候補の編集 |
| 提携店（将来） | 未定 | role=shop + shop_id | 自店の注文だけ見える |

## 方式

- **Better Auth** を apps/api に置く。drizzle アダプタで D1 に `user / session / account / verification` を持つ。
- **手段**: メール OTP（6 桁コード）を基本にする。パスワードは持たない（忘れる・漏れる・リセット画面が要る）。Apple / Google のソーシャルログインは Development Build 以降で追加（Expo Go ではリダイレクトが不安定）。Google を入れるなら Apple 審査の要件で Sign in with Apple も必須。
- **匿名ユーザー**: Better Auth の anonymous プラグインを使う。アプリ起動時に匿名セッションを作り、ギフトの下書き・候補・一言までは匿名で進める。リンク発行（`POST /gifts/:id/issue`）と決済の手前でサインインを求め、匿名ユーザーの持ち物を本アカウントに引き継ぐ（プラグインの linking で `gifts.giver_user_id` を付け替える）。
- **セッションの運び方**
  - アプリ: `@better-auth/expo` が Cookie を SecureStore に保存し、`hc` の fetch に Cookie ヘッダを付ける。`trustedOrigins` にアプリの scheme（`sakeapp://`）を入れる。
  - Web（将来の Web 版）: ブラウザは apps/web とだけ話す。apps/web が `/api/auth/*` と `/api/*` をサービスバインディングで API に転送し、`Set-Cookie` を中継する。Better Auth の `baseURL` は Web のオリジン。API の公開 URL はブラウザに出さない。
- **メール送信**: OTP の配信に Resend（無料枠）か Cloudflare Email Sending。staging では送信せずログに出す。

## 受け取りリンクの権限（トークン）

- `gifts.claim_token` は 128 bit 以上の乱数（base64url で 22 文字以上）。推測不能であることが唯一の防御なので、短縮や連番にしない。
- トークンで出来ること: 受け取りページの閲覧（贈り主の一言、一本の説明、配送状況）と、住所の送信（1 回だけ）。住所は送信後にトークンから読めない（配送状況のみ）。
- 期限: 発行から 30 日で失効（`claim_expires_at`）。失効後は贈り主が再発行できる（新トークン、旧トークン無効）。
- LINE で共有される前提なので、URL に個人情報を含めない。OGP も「日本酒が届きます」程度に留め、贈り主の本名や一言は OGP に出さない（プレビューはグループでも見える）。
- 受け取る側が後からアプリを入れて記録を付ける場合: アプリの「もらったリンクを開く」（Universal Link / App Link）でトークンを受け取り、サインイン後に `gifts.recipient_user_id` を紐づける。紐づけはトークンが有効な間だけ。

## 成人確認

- 受け取りページの送信時に「20 歳以上」の自己申告を必須にし、`orders.adult_confirmed_at` に時刻を記録する。
- 贈る側にも、アプリの初回とリンク発行時に同じ自己申告を置く（贈る側も飲酒年齢であることを前提にする）。
- 法的な販売主体は提携店なので、店側の確認手順に合わせて増やす。

## 認可マトリクス

| 操作 | 匿名 | 本人 | 受け取りトークン | admin |
| --- | --- | --- | --- | --- |
| 候補カタログの閲覧 | ○ | ○ | ○（選ばれた一本のみ） | ○ |
| ギフト下書き・候補・一言 | ○（自分のもの） | ○（自分のもの） | × | ○ |
| リンク発行・決済 | × | ○（自分のもの） | × | ○ |
| ギフトの状態閲覧 | ○（自分のもの） | ○（自分のもの） | ○（住所以外） | ○ |
| 住所の送信 | × | × | ○（1 回） | ○ |
| 住所の閲覧 | × | ×（贈り主も不可） | × | ○（店への受け渡しに必要な間だけ） |
| 記録の作成・閲覧 | × | ○（自分のものだけ） | × | ×（運営も読まない） |
| 「開けたよ」の受信 | - | ○（贈り主） | - | - |
| 注文の進行、候補の編集 | × | × | × | ○ |

原則:
- 贈り主は受け取る側の住所を一切見ない（店が発送する。贈り主に住所が要る場面がない）。
- 記録（tastings）は本人以外、運営も読まない。贈り主に渡るのは `gifts.opened_at` が立ったという事実だけ。
- `services/*` は「誰が」を引数で受け、所有者チェックを必ず service 側で行う（ルートでの漏れを防ぐ）。

## 実装メモ

- `middleware/session.ts`: `auth.api.getSession({ headers })` の結果を `c.set("user", …)`。未ログインは null のまま通す。
- `middleware/require.ts`: `requireUser`（匿名可）、`requireVerifiedUser`（匿名不可）、`requireRole("admin")`。
- admin の初期付与: 環境変数 `ADMIN_EMAILS` に含まれるメールでサインインしたら `user.role = "admin"` にする（Better Auth の databaseHooks）。
- レート制限: Better Auth 内蔵のものを OTP 送信と検証に使う。受け取りトークンの総当たり対策は Cloudflare の Rate Limiting ルール（無料枠）で `/claims/*` を絞る。
- 監査: `gift_events` に誰が何をしたかを残す（状態遷移はすべてイベント経由）。

## 決めていないこと

- LINE ログインを入れるか。受け取る側が LINE で来る以上、相性は良いが、審査と設定の手間がある。Phase 2 以降で判断。
- 受け取る側に「アカウントなしで記録だけ端末に残す」を許すか。「開けたよ」が送れないので、記録＝アカウント必須で始める。
